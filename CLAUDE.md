# issassist.helm — agent rulebook (the product assembly point)
Helm 3 chart (`Chart.yaml` `apiVersion: v2`, `version: 1.2.0`) that deploys the whole
stack. Style: [`../CLAUDE.md`](../CLAUDE.md) (Helm section).

## Branches and releases (agreed 2026/10/23)

Restated here because the root [`../CLAUDE.md`](../CLAUDE.md) is not under version control.

- **All work is an issue** in `IssTech/isstech-issues`, on the IssAssist GitHub Project.
  Start it with `/project-start <issue>` (alias `/start-project`), finish it with
  `/project-close` (alias `/close-project`).
- **Branch `<type>/<issue>-<slug>-<YYYYMMDD>`**, type `bug`, `fix` or `rfe` — e.g.
  `rfe/244-send-logs-to-support-20261023`. Cut from `origin/review`, same name in every
  repo the issue touches, and finished through a **PR into `review`**.
- **Release:** `/release-cut X.Y.Z` cuts `review-X.Y.Z` from `review`. A **human** merges
  `review-X.Y.Z` → `master`; no agent and no Claude session merges to `master`.
- **Rulesets (2026/10/24):** `review` and `review-*` cannot be deleted or force-pushed;
  `master` accepts changes only through a PR.
- **Hotfix:** cut from the latest `review`, not from `master`. `/project-start` lists the
  migrations, API and dependency changes in `master..review` and stops for a human to decide.
- **New features ship dark** behind a `values.yaml` flag — see *Release flow* below.

## This chart IS the product
The chart pins the 3 product image tags in `values.yaml`: `api.image` (issassist-api),
`webGUI.image` (issassist-webgui), `tsmAgent.image` (issassist-tsm-agent) — currently all
`ghcr.io/isstech/issassist-*:1.3`. It also bundles supporting images (postgres:17 x2,
kubernetes-secret-generator, the `superset` subchart). There is **no `releases/` folder**
in this repo today — if you need a BOM/version-tracking record, that mechanism does not
exist yet and would need to be built, not assumed.

## Module conditional pattern (actual, not `.Values.modules.*`)
There is no `modules:` key in `values.yaml` and no `{{- if .Values.modules.<name>.enabled }}`
pattern anywhere in `templates/` — do not use that pattern from memory. Gating is
per-component under real top-level keys: `global`, `api`, `webGUI`, `tsmAgent`, `pgAdmin`,
`clusterScoped`, `imageCredentials`, `kubernetes-secret-generator`, `superset`. Example:
`{{ if .Values.tsmAgent.enabled }}` in `templates/issassist/tsm-agent/deployment.yaml`.
Disabling `tsmAgent.enabled` removes its Deployment plus its dependent Postgres/Valkey
resources (`templates/dependencies/tsm-agent-postgres/`, `templates/dependencies/tsm-agent-valkey/`).
`pgAdmin.enabled` (default `false`) gates `templates/tools/pgadmin/` the same way.
The `superset` subchart uses `condition: superset.enabled` in `Chart.yaml` — follow that
pattern for any new conditional Helm dependency.

**Kasten and AvePoint have no chart-level toggle.** issassist-api has `kasten/` and
`avepoint/` integration packages (see `../issassist-api/CLAUDE.md`), but nothing in this
chart's `values.yaml` or `templates/` references either name — those integrations are
enabled today via issassist-api's own config/env vars, not via a Helm value. If you wire a
Helm-level enable/disable switch for them, follow the Kubernetes-first design rule in the
root `CLAUDE.md` (values.yaml key → ConfigMap → env var, never a hardcoded URL).

## Registry credentials

`imageCredentials.existingSecret` names a docker-registry Secret you created yourself, and
the chart references it instead of templating one. **Prefer it.**

The alternative — `imageCredentials.username`/`password` — still works and is kept so
existing installs keep working, but Helm stores user-supplied values in plaintext inside
the release secret and keeps a copy per revision. Anyone who can read secrets in the
namespace, or run `helm get values`, can read the token, and **no repository secret scanner
ever sees it** because it is not in a repository. A live token was found sitting in
staging's release values in 2026-09; that is why the option exists.

The pull-secret name is resolved through `issassist.imagePullSecretName` in all six places
that reference it, so the two paths cannot drift apart.

## IssTech dashboard connection

`api.issTechConnect` carries the settings that let a customer's issassist-api reach
**our** dashboard. It does **not** install a dashboard — that runs at IssTech and is never
deployed at a customer site. The key is named `issTechConnect` rather than `dashboard`
precisely because the latter read as "install a dashboard here" and caused that confusion.

Leave `url` empty and nothing renders at all: no env vars, no Secret, and the application
registers no reporting job. Configuring it is the opt-in; there is no separate switch.

`activationCode` is a credential and goes in a Secret, not the ConfigMap.
`IA_DASHBOARD_SECRET_KEY` is generated by kubernetes-secret-generator and **must survive
upgrades** — it encrypts the enrolment credential at rest, so regenerating it makes that
credential undecryptable and forces re-enrolment with a fresh code from IssTech.

## Secrets
cert-manager issues internal TLS (17 `Certificate` resources under `templates/certificates/`);
kubernetes-secret-generator creates passwords (9 resources under `templates/accounts/`) —
never hardcode secrets in templates. Use `secretKeyRef` (used throughout
`templates/issassist/api/deployment.yaml` and `templates/issassist/tsm-agent/deployment.yaml`),
not plain env values.

## Other values worth knowing
- `imageCredentials` — GHCR pull secret config; required per the root README install flow.
- `charts/` — vendored subcharts (`kubernetes-secret-generator`, `superset`).

## Local test path
`values.local-test.yaml` does **not currently exist** in this repo — there is no MicroK8s
Tier-2 test values file today despite the root CLAUDE.md's Tier-2 testing convention. If
you add one, keep it working at all times; a change that breaks it should block the
release once this path exists.

## Release flow (agreed 2026/10/23)
**The chart version is the IssAssist product version** — the bundle. Each component keeps
its own version and is pinned **exactly** in `values.yaml` (`issassist-api:1.5.1-203`, never
`:1.3`), so one chart always means the same images. A release that changed only the api is
a new bundle with the other components left where they were.

- **Patch** (1.5.0 → 1.5.1) when every issue since the last tag is a `fix` or `bug`;
  **minor** (→ 1.6.0) as soon as one `rfe` is in; **major** is set by a human. Until this is
  computed automatically, apply the rule by hand.
- The floating `:1.3` tags above are the current state, not a pattern to copy.

1. Project branches merged into `review` in each component repo, through PRs.
2. `/release-cut X.Y.Z` cuts `review-X.Y.Z` from `review`; after that only fixes go in,
   and they are merged back to `review`.
3. Pin the exact component tags in `values.yaml`; set `Chart.yaml` `version` to X.Y.Z.
4. A **human** merges `review-X.Y.Z` → the default branch (`main` in issassist-api,
   `master` elsewhere) in each repo and tags `vX.Y.Z` here.
5. Publish chart + offline bundle (for air-gapped Dark Site customers).

**Beta features** get a `values.yaml` flag that defaults to off. Staging turns it on;
customers keep the default. Accepting the feature means flipping the default in the next
release; rejecting it means a PR that removes both the code and the flag.
