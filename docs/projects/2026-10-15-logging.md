# Logging: say why a Storage Protect connection or sync failed, and keep it — issassist.helm

## Summary

A failed connection to an Operations Center used to leave three blanks:
- the page said only "Could not connect to the Operations Center.";
- the API's log said nothing;
- the Processes page had no run.

The pod that hit the failure was often restarted before anybody looked, taking the only log with it.

Now:
- the agent names the cause and what to do;
- each failure is logged once, with structured fields;
- page actions are runs on the Processes page;
- both services keep their log lines in their own database, for the Logs page and a support download.

Mission [IssTech/IssAssist-Mission#241](https://github.com/IssTech/IssAssist-Mission/issues/241). The mockup was approved on 2026/10/15: `issassist-webgui/docs/mockups/2026-10-15-logging/`.

## Why

Found during the customer test against `tsmoc02.prd.infra.g30.se:11090` on 2026/10/14.
- A self-signed certificate showed as "Could not connect". The client caught `ClientConnectorSSLError`, but aiohttp raises its sibling `ClientConnectorCertificateError`, which fell through to the generic branch.
- Nothing was logged in either service.
- *Sync* from the page left no run.
- API restarts during the first start dropped the only log.

The full reasoning, the design and the security review are in the API record, `issassist-api/docs/projects/2026-10-15-logging.md`.

## What changed in this repo

**`logging.*` values → ConfigMap → env.**
- The four keys in `values.yaml` render `templates/issassist/logging-configmap.yaml` (`issassist-logging`).
- The API and TSM agent Deployments read that ConfigMap with `envFrom`.
- The template validates with `fail`: an unknown level or format, or `keepDays` outside 1–365, stops the install with a message. **`keepDays: 0` is refused**, not taken as "keep nothing".
- Each Deployment carries a `checksum/logging` annotation, so changing a value restarts its pods. Env is read once, at start.

**Pod and node on every line.** `IA_POD_NAME` and `IA_NODE_NAME` come from the Downward API. The agent runs three replicas on different nodes, and a network fault often affects only one of them.

**API startup probe.** `templates/issassist/api/deployment.yaml`: `GET /api/v1/info/`, every 10 s, up to 60 times (10 minutes). The first start runs every migration. Without the probe, the liveness probe killed the API mid-migration after 30 s, and each restart threw away the only log of why. That happened three times on the customer test cluster.

**`RELEASE.md` is new in this repo**, starting with these keys.

## Configuration

| Key | Default | Meaning |
| --- | --- | --- |
| `logging.level` | `INFO` | Lowest level written to the pods' output: `DEBUG`, `INFO`, `WARNING` or `ERROR`. DEBUG is never stored in the database. |
| `logging.format` | `text` | `text`, or `json` for Loki, Elastic or Splunk. Pod output only. |
| `logging.keepDays` | `30` | Days a line is kept for the Logs page and the support download (1–365). |
| `logging.storeFrom` | `INFO` | Lowest level kept in the database: `INFO`, `WARNING` or `ERROR`. |

## How to verify

```bash
helm template t . | grep -A6 'name: issassist-logging'           # the four IA_LOG_* values
helm template t . --set logging.keepDays=0 2>&1 >/dev/null | head -1
#   Error: … logging.keepDays must be between 1 and 365, not 0
helm template t . --set logging.level=VERBOSE 2>&1 >/dev/null | head -1
#   Error: … logging.level must be DEBUG, INFO, WARNING or ERROR, not "VERBOSE"
```

**`helm lint` fails on a missing `kubernetes-secret-generator` dependency.** It fails the same way on `review`, so this is pre-existing and not caused by this change.

## Deployment & rollback

- Deploy the chart change in the same upgrade as the new API and agent images.
- Older images ignore the extra env vars, so the chart can go first.
- **Rollback:** `helm rollback` to the previous revision. The ConfigMap is removed and the pods restart without the probe.
