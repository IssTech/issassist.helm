## #526 P3: Postgres and Valkey were NodePorts

`templates/dependencies/*/service.yaml` hardcoded `type: NodePort` with ports 30101–30106 and
no values override (already listed under "Known issues" in IssAssist-Docs
`getting-started/helm-installation.md`, which verified port 30101 reachable from an unrelated
namespace).

**What.** Each Service reads `<component>.<postgres|valkey>.service.type` (default `ClusterIP`,
also when the key is missing from an older values file) and, for `NodePort` only,
`.nodePort` defaulting to the old fixed port, so opting back in is a one-key change that
restores the exact old port. Any other type fails the render — `LoadBalancer` would publish a
database beyond the node network.

**What used the node ports.** Nothing in the chart: the API (`configmap.yaml`: `api-postgres`,
`api-valkey`), pgAdmin (`servers.json`: `api-postgres:5432`, `tsm-agent-postgres:5432`),
Superset (`tsm-agent-postgres:5432`) and the init containers all use Service DNS. Outside it:
`.idea/dataSources.xml` in issassist-api and issassist-tsm-agent point a developer's IDE at
`any.app.local:30101–30104` (dev convenience; use port-forward or opt back in), and
IssAssist-Docs `helm-installation.md` "Known issues" describes the NodePorts as a defect —
it needs updating to say fixed in 1.5.0 (not done here: that repo is on `main`).

**Upgrade.** Helm patches the Service from NodePort to ClusterIP in place; the old manifest's
`nodePort` is removed by the three-way merge, which the API server requires for that change.
Not exercised against a live cluster in this change.

**Tests.** `scripts/check_datastore_services_render.sh`: 29 checks (each Service ClusterIP with
no nodePort by default; opt-in per Service restores its old port; one opt-in leaves the others
closed; a removed key stays ClusterIP; LoadBalancer refused). Against the old templates 16 fail.

## #372: the CA for the public-URL self-check

The self-check calls the public URL, so it meets the ingress certificate. With
`issuerType: disabled` (default) that is `self-signed-ingress-cert`, issued by the `root-issuer`
selfSigned ClusterIssuer, not by `issassist-ca` — so the internal CA is the wrong thing to
mount. cert-manager writes a selfSigned certificate into its own `ca.crt`.

**What.** `api.selfCheck.caBundle.{secret,configMap,key}`. Operator's Secret/ConfigMap first;
else, with `issuerType: disabled`, `self-signed-ingress-cert` key `ca.crt`; else nothing (public
issuer, public store). Volume `items` projects only the CA key (the ingress Secret also holds
`tls.key`); a directory mount, not `subPath`, so renewal (`rotationPolicy: Always`, 1-year
`certDuration`) reaches the pod; `optional: true` so a missing CA does not stop the API — the
app then refuses the check with "cannot be read".

**Tests.** `scripts/check_self_check_render.sh`: 13 checks; against the old templates 8 fail.
All render scripts: ai_analysis 138, api 16, kasten_connector 13, datastore 29, self_check 13 ok.
`helm lint` fails on `review` already (`chart metadata is missing these dependencies:
kubernetes-secret-generator`), unchanged by this.
