# Chart CI: helm lint, render checks and kubeconform (2026/11/20)

Missions: IA-0046 (isstech-issues #531, helm half) and IA-0016 item #366
("make helm lint work without manual dependency build"). Branch
`fix/chart-ci-20261120`, cut from `review`. Release note: `RELEASE.md`, 1.6.0.

## Why

The chart had no CI at all. `helm lint` failed on `review` with

```
[ERROR] .: chart metadata is missing these dependencies: kubernetes-secret-generator
```

and the `scripts/check_*_render.sh` scripts — 232 assertions about what the chart must
and must not render, several of them security findings — ran only when somebody
remembered. Gate ② in the root CLAUDE.md: a test that does not run in CI is not a gate.

## The lint fix

`charts/` holds two vendored subcharts. Helm includes everything in `charts/`, listed or
not, but `helm lint` refuses a subchart that `Chart.yaml` does not name. Only `superset`
was named.

`kubernetes-secret-generator` is now listed — version `3.4.1`, no repository, **no
condition**. There is no `kubernetes-secret-generator.enabled` key in `values.yaml` and no
template gates on one: the subchart has always been installed unconditionally, and every
password Secret in `templates/accounts/` and `templates/issassist/` relies on its
controller. A `condition:` pointing at a key that does not exist would also have rendered
identically (Helm treats a missing condition path as enabled), but it would suggest a
switch that is not there. The only knob the values actually use is
`kubernetes-secret-generator.rbac.clusterRole`, which the subchart reads itself.

`Chart.lock` is now committed. With no repository on either dependency,
`helm dependency build` prints "Assuming it exists in the charts directory" and downloads
nothing; with the lock committed it also fails if somebody changes `dependencies:` in
`Chart.yaml` without regenerating the lock (`helm dependency update`).

### Proof the rendered chart did not change

`helm template` before (origin/review) and after the change, compared with `cmp`:

| helm | values | result | lines |
|---|---|---|---:|
| v3.22.1 | defaults | identical | 5855 |
| v3.22.1 | `clusterScoped.create=false`, `kubernetes-secret-generator.rbac.clusterRole=false` | identical | 5778 |
| v3.22.1 | `superset.enabled=true`, `pgAdmin.enabled=true` | identical | — |
| v4.2.0 | defaults | identical | 5918 |
| v4.2.0 | staging-like (as above) | identical | 5839 |

Helm 3 and Helm 4 render the same objects (same kinds and names). Their output differs
in blank lines and in one field: the subchart's ServiceAccount renders
`automountServiceAccountToken:` with an empty (null) value under Helm 3 and leaves the
field out under Helm 4. Both mean the Kubernetes default (mounted), and the controller
needs its token. Pre-existing, in the vendored subchart, not touched here.

## What the workflow runs

`.github/workflows/chart.yml`, on pull requests into `review` and `master` and pushes to
`review`, as a matrix over Helm v3.22.1 (customer installs, README flow) and v4.3.1:

1. `helm dependency build --skip-refresh`, then fail if `Chart.lock` or `charts/` changed.
2. `helm lint --strict` with the defaults and with each `ci/*-values.yaml`.
3. `helm template` with the defaults, `ci/staging-like-values.yaml` and
   `ci/all-optional-values.yaml`; object counts and hashes go to the run summary.
4. Every `scripts/check_*_render.sh`, plus `scripts/check_readonly_role.sh` without
   `--live`. A script that exits non-zero, or prints no `ok` line at all, fails the step.
5. `kubeconform -strict` on each render, against Kubernetes **1.30.0** (the documented
   minimum: ValidatingAdmissionPolicy) and **1.36.0** (newest with published schemas; the
   Bob admission policy was tested live on 1.36). The Kubernetes schemas come from
   yannh/kubernetes-json-schema pinned to commit `e0c72a1` (2026/10/31); cert-manager kinds
   from the datreeio CRDs-catalog pinned to commit `3eb90d4` (2026/10/25).
   `-ignore-missing-schemas` is deliberately **not** used: a kind with no schema fails.

Not run in CI, and why:

- `scripts/check_bob_admission_live.sh` needs a throwaway Kubernetes API server.
- `scripts/check_readonly_role.sh --live` needs docker and a TLS Postgres.

### Pinning

Helm and kubeconform are downloaded from their release URLs and checked against a
SHA-256 in the workflow (cross-checked against the checksums in the Helm release notes).
The only action used is `actions/checkout`, pinned by commit as in the other IssAssist
repos. To bump a tool, change the version and the checksum together.

### Render sets in `ci/`

- `staging-like-values.yaml` — a shared cluster: no cluster-scoped RBAC from the chart or
  the subchart.
- `all-optional-values.yaml` — superset, pgAdmin, the Kasten connector with inventory, the
  read-only Postgres role and the AvePoint run check, the AI debug wizard and the Bob run
  namespace, so kubeconform sees templates that the defaults leave out (110 objects,
  including the ValidatingAdmissionPolicies). Image references are placeholder digests.

`ci/` and `.github/` are in `.helmignore`, so they are not packaged with the chart.

## Proven to fail (gate ②)

Each check step was broken once on this branch, seen red in both Helm jobs at exactly
that step (the earlier steps green), and reverted in the next commit:

| step | deliberate break | red run |
|---|---|---|
| `helm dependency build` | secret-generator `3.4.1` → `3.4.2` in `Chart.yaml` only: "the lock file (Chart.lock) is out of sync" | [44737109592](https://github.com/IssTech/issassist.helm/actions/runs/44737109592) |
| `helm lint --strict` | a template that dereferences a missing value | [44737218359](https://github.com/IssTech/issassist.helm/actions/runs/44737218359) |
| `helm template` | a template that calls `fail` only in namespace `issassist` (lint renders in `default`, so lint stays green) | [44737330089](https://github.com/IssTech/issassist.helm/actions/runs/44737330089) |
| render checks | `tsmAgent.tasks.heartbeatTimeout` default `300` → `301`: "231 ok, 1 FAIL" | [44737675579](https://github.com/IssTech/issassist.helm/actions/runs/44737675579) |
| kubeconform | `replicaz: 1` in the tsm-agent Deployment spec: Invalid 1 in each of the six renders × versions | [44737827017](https://github.com/IssTech/issassist.helm/actions/runs/44737827017) |

The first attempt at the render-check proof
([44737424324](https://github.com/IssTech/issassist.helm/actions/runs/44737424324)) went red
for the right reason but printed nothing: Actions runs each step with `bash -e`, and
`log=$(bash script)` aborted the step on the first failing script. The step now catches the
exit code, which is why the second run shows the FAIL line and the 231/1 count.

## Open

- Making `Chart` a required status check on `review` and `master` is a branch-protection
  setting for the repository owner.
- The `superset` subchart declares bitnami `postgresql` and `redis` dependencies that are
  not vendored. They are disabled (the chart runs its own `superset-postgres` and
  `superset-valkey`), so nothing renders from them, but a `helm dependency build` inside
  `charts/superset` would try to fetch them.
